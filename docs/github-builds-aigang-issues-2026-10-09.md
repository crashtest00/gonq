## Open AI Gang bugs

1. Setup docs and init-project.sh omit the PAT permission `Actions: Read and write`, which native builds need (docs/UserGuide.md:49-54, scripts/init-project.sh:674, :801).
2. jenkins/scripts/trigger-native-build.sh:25 silences dispatch errors and reports `STATUS=unknown`.
3. No automatic native build in local mode, and no doc telling the owner a Release is required (handlers.js:113-118, store.py:527-540).
4. Release jobs need `/home/aigang/ai-gang/projects/<name>/src`, which Jenkins' compose never mounts (jenkins.yaml:93, :223).
5. Release jobs would run `git checkout`/`push` in a shared agent workspace with a UID mismatch and no git credentials (jenkins.yaml:107-110).
6. Preview URL hard-coded to `https://` with no port (jenkins.yaml:128).
7. DevOps agent verification runs in the shared /workspace (stale untracked files can mask a clean-runner failure; it didn't matter this time, see the 16:18 correction), and the image has no YAML parser for the mandatory parse check.
8. Jenkins' PR pipeline can't detect a broken GitHub Actions workflow and auto-merges it.
9. A dev build killed by a Jenkins restart publishes pipeline_retry as a real failure; unattributable retries are only logged.
10. An agent session that ends without `a2a-submit` goes unnoticed; its merged PR can't be attributed and the item stays `in-progress` (rework redispatch of 90bb15f4).
11. Admin silently ignores release-detail inline fields the user can't edit (302, nothing saved).
12. ScrumMaster's release triggers are a silent no-op without JENKINS_URL and still log "Triggered" (jenkins.js:11-15, :40-42).
13. JENKINS_URL is never set for ScrumMaster, and the root .env value (`localhost`) is wrong from inside its container (init-jenkins.sh:98-108).
14. Desktop scaffold has no `.gitattributes`, and no CI runs Windows before a Release, so CRLF bugs surface only at release time.
15. Abandoning a Release leaves its `release/<sha>` branch and prod PR open; no documented re-cut path after a failed native build.
16. A production server makes no sense when the release target is not a production server, yet production-promote requires a prod server deploy, before the tag, even for desktop projects (whose release target is a GitHub Release); a missing server leaves prod merged with no tag or Release (jenkins.yaml:224-262).
17. production-promote's "Confirm on the release" stage always crashes (`No such property: body`, jenkins.yaml:279 escaping), so every promotion is reported FAILURE.
18. production-promote's failure comment always says the prod PR is still open, even when it merged.
19. The desktop handbook doesn't say macOS builds are Apple-silicon only (macos-latest → aarch64 .dmg).
